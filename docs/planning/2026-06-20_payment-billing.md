# 결제·정기구독 플로우 (기획)

> 작성일: 2026-06-20 · 상태: 기획(미착수). 요금제 4단계(무료3/베이직5·9900/프로20·29900/엔터프라이즈)는 배포 완료, 결제 자동화만 남음.

## 0. 목표
사장님이 **앱 안에서 직접 카드 등록 → 자동 결제**로 유료 전환되게 한다. (현재는 카카오 문의 → 운영자가 콘솔에서 수동 부여)

## 1. 현재 자산 (절반은 이미 있음) ✅
- `businesses.plan` — 요금제 (free/basic/pro/enterprise)
- `businesses.plan_expires_at` — 유료 만료일
- **만료 도달 시 자동 정지 미들웨어** (is_active=0, suspended_at 기록)
- **만료일 미래로 갱신 시 자동 활성화** (admin plan_expires_at PATCH)
- → **결제 성공 = `plan` 업그레이드 + `plan_expires_at`를 +1개월** 로 갱신하면 기존 정지/활성 로직과 그대로 맞물림.

## 2. PG사 선택
| 후보 | 특징 | 비고 |
|---|---|---|
| **토스페이먼츠 (추천)** | 정기결제(빌링키) 지원, 문서·DX 우수, 결제위젯 | 가맹점 심사 + 빌링 별도 신청 필요 |
| 포트원(아임포트) | 여러 PG 묶음, 정기결제 | 추상화 좋으나 한 단계 더 |
| 카카오/네이버페이 직접 | 간편결제 | 정기결제는 제약 |

→ **추천: 토스페이먼츠 빌링(자동결제)**. 단일 PG로 시작, 필요 시 포트원으로 확장.

## 3. 결제 모델 — 정기결제(빌링키)
1. 사장님이 카드 1회 등록 → 토스가 **빌링키(billingKey)** 발급 → 우리 서버에 저장
2. 첫 결제 즉시 실행 → `plan` 업그레이드 + `plan_expires_at = 오늘+1개월`
3. 매월 만료 임박 시 **스케줄러가 빌링키로 자동 청구** → 성공 시 +1개월 연장
4. 실패 시 재시도(dunning) → 최종 실패 시 만료 → **기존 미들웨어가 자동 정지**

## 4. 전체 흐름 (시퀀스)
```
[업그레이드 클릭] → 플랜 선택(베이직/프로)
   → 토스 결제창(카드 등록, 빌링키 발급)
   → authKey 콜백 → 서버: 빌링키 발급 API → billingKey 저장(customerKey 매핑)
   → 서버: 첫 결제 요청(amount=플랜가) → 성공
   → businesses.plan=선택플랜, plan_expires_at=+1개월
   → 대시보드 유료 기능 즉시 해제

[매월 스케줄러(일 1회)]
   → plan_expires_at가 N일 내 만료 + 유료 + billingKey 보유 사업장 조회
   → 빌링키로 결제 요청 → 성공: plan_expires_at +1개월 / 실패: 재시도 큐
   → 최종 실패: 만료 도달 → 미들웨어 자동 정지 + 안내
```

## 5. DB 스키마 추가 (안)
- `subscriptions` (사업장↔빌링키)
  - business_id, customer_key, billing_key(암호화 저장), card_last4, plan, status('active'|'past_due'|'canceled'), started_at, next_billing_at
- `payments` (결제 이력)
  - business_id, amount, status('paid'|'failed'), pg_tx_id, paid_at, fail_reason, receipt_url
- (또는 businesses에 billing_key/customer_key 컬럼 + payments 테이블만)

## 6. 서버 구현
- 토스 빌링 연동: 빌링키 발급(`/v1/billing/authorizations/issue`), 결제(`/v1/billing/{billingKey}`)
- 웹훅 수신(결제 상태 비동기 갱신) + 멱등 처리
- **정기결제 스케줄러**: 기존 backup `setInterval` 패턴 재사용 가능(일 1회) 또는 Railway cron
- env: `TOSS_SECRET_KEY`, `TOSS_CLIENT_KEY` (Railway + 로컬)

## 7. 프론트
- 업그레이드 페이지: 플랜 비교표 + 토스 결제위젯/SDK(카드 등록)
- 결제 내역/영수증, 다음 결제일 표시, 카드 변경, **해지** 버튼
- 기존 업그레이드 CTA(카카오 문의)를 이 페이지로 교체

## 8. 외부 의존성 / 리드타임 ⚠️ (사용자 직접)
1. **토스페이먼츠 가맹점 가입** — 사업자등록증, 정산계좌. 심사 수일
2. **정기결제(빌링) 사용 신청** — 별도 심사
3. 키 발급(TEST/LIVE) → env 주입

## 9. 결정 필요 (비즈니스)
- [ ] **PG사** — 토스페이먼츠로 확정?
- [ ] **부가세(VAT)** — 9,900/29,900원이 VAT 포함가? 별도(+10%)?
- [ ] **무료체험** 제공? (예: 14일 무료 후 자동결제)
- [ ] **결제 실패 유예기간** — 며칠 재시도 후 정지? (예: 3일·3회)
- [ ] **중도 해지/환불 정책** — 월 중 해지 시 일할 환불? 남은 기간 사용 후 미갱신?
- [ ] **결제 주체 인증** — 사장님 식별(현재 PIN/구글). 빌링키는 사업장 단위 매핑 → 13장 참고
- [ ] **신규 가입 구글 로그인 강제 여부** — 13장. 권장: 신규는 구글 owner 연결 필수 + PIN 병행, 기존은 grandfather

## 10. 법적·정책
- 자동결제 **사전 고지 + 동의** 화면 필수
- 전자상거래법: 청약철회·환불 규정 고지, 결제 영수증 발급
- 빌링키는 민감정보 → 서버 암호화 보관, PCI 범위는 토스가 처리(우리는 카드번호 미보관)
- 이용약관/개인정보처리방침에 결제·정기과금 항목 추가 (기존 legal 문서 갱신)

## 11. 구현 단계 (Phase)
- **B1**: 토스 가맹점·빌링 신청(외부, 리드타임) + env
- **B2**: DB(subscriptions/payments) + 빌링키 발급·저장 + 첫 결제 → plan 반영
- **B3**: 업그레이드 UI(결제위젯) + 결제 내역/해지
- **B4**: 정기결제 스케줄러 + 실패 dunning + 웹훅
- **B5**: 환불·영수증·약관 + 운영자 결제현황 콘솔

## 13. 신원확인 / 결제 권한자 식별
**문제:** 현재 "사장/관리자" 식별 기준은 ① PIN 보유(지식 기반, 신원 검증 없음) ② 연결된 구글 계정(이메일 신원만)뿐. 즉 시스템은 *진짜 그 사업장 사장인지* 검증하지 않음. PIN만 운영하면 PIN 아는 사람=관리자. → 결제·세금계산서·분쟁 대응에 근거 약함.

**신원 강화 수단 (한국 실무):**
| 방법 | 강도 | 비고 |
|---|---|---|
| 구글 OAuth owner 연결 | 중 | 이미 구현됨, 검증된 이메일 |
| 휴대폰 본인인증(PASS/문자) | 높음 | 한국식 표준 신원확인 |
| 사업자등록번호 + 진위확인(국세청 API) | 높음 | 세금계산서·B2B에 어차피 필요 |
| 결제 카드 본인인증(토스) | 중~높음 | "돈 내는 사람=사장" 자연 검증 |

**권장 설계:**
1. **결제(업그레이드) 시 사업자등록번호 입력 + 카드 본인인증** → 유료 전환 시점에 "검증된 사장"이 식별되고 세금계산서도 해결. (결제 흐름에 자연 통합)
2. **owner = 구글(또는 휴대폰 인증)된 1인**, 그 외는 PIN 관리자(하위). 빌링키·결제권한은 owner에 귀속.
3. **PIN은 신원 보증이 아니라 "사업장 접근 비번"**임을 명확히. PIN 분실 복구는 owner(구글) 로그인 또는 운영자 재발급으로.

**신규 가입 구글 로그인 강제 — ✅구현됨(2026-06-20):** 공개 셀프가입(`/create`)을 **구글 먼저** 흐름으로 전환. 구글 신원확인 → 1회용 signup 토큰 → 이름·PIN 입력 → owner_user_id 연결된 사업장 생성. PIN 병행 유지. createBusiness는 signup_token 없으면 403(SIGNUP_GOOGLE_REQUIRED). 운영자 대행 프로비전은 그대로(구글 불가 사장 예외). 기존 PIN 전용 사업장 grandfather(무영향).

**(설계 근거)**
- 신규 사업장은 **구글 owner 연결 필수**(검증된 신원 + PIN 분실 복구 경로 확보 + 결제 대비), **PIN은 일상·키오스크용으로 병행 유지**.
- 순수 구글-only로는 안 감(키오스크/공용단말·비IT 사장 마찰). 구글 불가 사장은 **운영자 대행 프로비전**으로 예외 처리.
- **기존 PIN 전용 사업장은 grandfather**(강제 전환 안 함, 안내만).
- 효과: 오늘 이후 가입분부터 "검증된 owner + 복구 가능 + 결제 준비"가 기본값이 됨.

## 12. 핵심 강점
기존 `plan_expires_at` + 자동 정지/활성 미들웨어 덕분에 **"결제 성공 → 만료일 연장"** 한 줄이면 구독 라이프사이클의 절반이 동작한다. 신규 구축은 빌링키 연동 + 스케줄러 + UI 중심.
